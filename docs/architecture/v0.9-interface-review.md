# v0.9 Public Interface Review

Status: reviewed for the v0.9 repository candidate

This review classifies the interfaces that exist in v0.9. It does not make
every public Rust item a product or post-1.0 compatibility promise. The exact
item-level interface is the rustdoc generated from each package root; this
record supplies the caller obligations that a type signature alone cannot
carry: authority, ordering, limits, side effects, recovery, and support class.

The classifications are:

- **v1 candidate** — reusable repository behavior included in the v0.9
  compatibility surface;
- **version-coupled adapter-author seam** — public so official Source adapters
  can implement it, but coupled to the current Source contract;
- **test support** — opt-in fault or generated-fixture behavior, never a
  production compatibility promise; and
- **private application surface** — callable application composition whose
  syntax and facade remain pre-product and may change with its host.

## Ordering and determinism review

The reusable interfaces expose ordering only where it has domain meaning:

- Source Batches retain Source order and Point ordinals.
- index candidate spans are canonical and conservative; hierarchy identity is
  deterministic for the same verified Source and recipe.
- Workspace Point Sets, Point rows, Revisions, transitions, and audits use
  canonical Point/lineage ordering.
- Terrain vertices, faces, descriptors, QA results, LandXML, reports, and
  Round-Trip Evidence use canonical encodings and hashes.
- render updates use explicit generations and versions; View plans use stable
  deterministic priority rather than map or allocation order.

No supported caller must know an index frame, Workspace block, Point Set spill,
journal frame, XML parser event, triangulation arena, GPU binding, or staging
filename. Those remain implementation-local. Deleting any owning module would
therefore force its authority, limit, ordering, and recovery rules back into
multiple callers rather than merely remove a pass-through.

## Limits and performance review

Every I/O or potentially scale-dependent reusable interface accepts an
explicit limit value or uses a documented default limit type. Limits are hard
failure gates, not allocator-reservation hints. Batch and job interfaces are
cooperatively cancellable and publish complete summaries only at their normal
terminal state.

Performance classes are deliberately narrow:

- value validation, protocol state, and View planning are in-process CPU work;
- Source, index, Workspace, terrain, QA, export, and qualification are bounded
  local I/O/CPU jobs or pull streams;
- wgpu methods record host-owned GPU work and never own submission; and
- Criterion observations apply only to their documented generated scale and
  reference machine. They are not latency service-level agreements.

## Error and compatibility review

Public reusable modules use typed errors with bounded diagnostics. Durable
owners distinguish invalid request, unsupported/corrupt state, resource or
cancellation failure, conflict, and indeterminate publication where callers
must reconcile before retrying. Demo-private failures additionally name the
Run/Operation/Revision, stage, certainty, and one recovery action when those
facts are available.

Cargo package version, persisted disk/semantic version, recipe/algorithm
version, and output schema remain independent. v0.9 freezes version-1 readers;
it does not invent a version-2 migration. Authoritative bytes fail closed and
are preserved, rebuildable index bytes follow explicit rebuild policy,
temporary bytes have owner-recognition cleanup only, and caller-owned outputs
are reconciled only when their exact bytes match.

## Evidence used for the review

The classification is exercised by package rustdoc, public interface tests,
official examples, generated process callers, persistence fixtures, fault
tests, Criterion benchmarks, and local GPU acceptance listed in
`CONTRIBUTING.md`. Passing those repository checks establishes only the
declared technical surface. It does not establish licensed production-data,
downstream-product, vendor, firm, paid-use, conversion, labor-savings, or
support-team evidence.
